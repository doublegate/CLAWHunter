# CLAWHunter v3.4.0

Release date: 2026-08-09

CLAWHunter v3.4.0 repairs the interactive payload, which could not run from the
Pager UI in any earlier release, and hardens loot permissions and release
packaging. There are no protocol changes: fingerprinting, scan, and assessment
behaviour is unchanged from v3.3.0.

**Upgrading is strongly recommended.** On v3.3.0 the user payload fails
immediately when launched from the device.

This is also the first release validated on physical Pager hardware, and that
validation is what surfaced the launch defect.

## Highlights

- **The interactive payload now starts from the Pager UI.** Previously it failed
  instantly with `Install Error / CLAWHunter common.sh was not found`, because
  the firmware runs a copy of the payload from `/tmp` rather than the installed
  file.
- **A rejected picker value no longer freezes the device.** An unbounded retry
  loop redrew the error dialog forever, escapable only by power-cycling.
- Local address and interface detection is centralised into two validated
  helpers with layered fallbacks — defensive hardening rather than a bug fix.
- Loot is no longer world-readable. Reports, logs, and the loot directory were
  created at 0644/0755 despite naming third-party hosts and recording harvested
  evidence about them.
- The loot permission guard fails closed: the payload refuses to run rather than
  write evidence into a directory it could not secure.
- `harvest.py` writes its report atomically at 0600, which also makes the write
  durable on a device that can lose power mid-scan.
- Release archives are now reproducible across hosts, not only across two builds
  on the same host.
- v3.3.0's standing "physical validation not performed" warning is discharged
  for 14 checks against real hardware, and narrowed to the surfaces that still
  require a human at the device.

## Upgrade Notes

Reinstall over an existing v3.3.0 installation; the installer overwrites at the
file level and no layout has changed.

```bash
scp -r clawhunter-v3.4.0 root@172.16.52.1:/tmp/
ssh root@172.16.52.1 '/tmp/clawhunter-v3.4.0/scripts/install-pager.sh'
```

Two upgrade effects worth knowing:

- An existing `/root/loot/clawhunter` directory is tightened to 0700 the first
  time a v3.4.0 payload runs. **Reports written by v3.3.0 keep their original
  0644 mode** — only newly written reports are created 0600. Run
  `chmod -R go-rwx /root/loot/clawhunter` once if historical loot matters.
- If that directory cannot be secured, the payload now exits with
  `CLAWHunter: refusing to run: cannot secure loot directory ...` instead of
  continuing. That is intended: it is the failure this release exists to
  prevent.

## Install and Verify

```bash
sha256sum -c clawhunter-v3.4.0-pager.tar.gz.sha256
tar -xzf clawhunter-v3.4.0-pager.tar.gz
cd clawhunter-v3.4.0
sha256sum -c SHA256SUMS
./scripts/install-pager.sh
```

Both `-c` checks must run from the directory their manifest is written against,
but for different reasons. The adjacent `.sha256` names the archive by bare
basename, so verify it from the directory holding the archive. The internal
`SHA256SUMS` is generated by `find .` and stores paths relative to the package
root (`./docs/...`, `./lib/common.sh`), so verify it from inside the extracted
`clawhunter-v3.4.0` directory. Running either from elsewhere reports
`No such file or directory` and `FAILED open or read`, which looks like
corruption rather than a wrong working directory.

## Technical Changes

### Payload resource resolution

The Pager firmware does not execute an installed payload in place. It prepends a
prelude and writes the result to `/tmp/payload-<random>.sh`, then runs the copy:

```bash
#!/bin/bash
PATH="$PATH:/mmc/bin:/mmc/sbin:/mmc/usr/bin:/mmc/usr/sbin"
. /lib/hak5/commands.sh
. /lib/hak5/pineapple.sh
```

All three payloads derived their resource directory from `$0`, which under that
launcher names a temp file with no `common.sh` beside it. Every branch of the
resolution chain is relative to that same wrong directory, so all three missed
and the install-error dialog fired. `BASH_SOURCE` is not a fix: the firmware
copies the file, so it reports the same temp path.

Resolution now takes the first candidate that actually contains payload
resources, in order: `_PAYLOAD_HOME`, `PAYLOAD_HOME`, `PWD`, `dirname "$0"`. The
firmware exports the first and sets the third; `$0` still covers manual,
repository, and staged invocation. The library search adds
`/root/payloads/lib/common.sh` as a final absolute fallback, mirroring what
`_resolve_harvest_py` already did — which is precisely why the harvest engine
was immune to this failure while the library resolution was not.

Two other properties of that prelude are worth knowing, both now recorded in
`AGENTS.md`: the `DUCKYSCRIPT_*` status constants arrive as **non-exported**
shell variables, so an `env` dump will not show them even though they are set
and every comparison against them works; and eMMC paths are already on `PATH`
before a payload starts.

### Bounded picker retries

The IPv4 and port pickers ended an invalid value with a bare `continue`,
re-opening the picker with no cap and no exit. Any condition that makes a picker
keep returning an unusable value lands there. Consecutive rejections are now
capped at three, after which the payload exits cleanly with a stated reason. The
counter resets after every accepted value, so a typo costs one retry rather than
the session.

### Loot permissions

`lib/common.sh` sets `umask 077` before the first write. This covers the loot
directory, every log and JSON report, the checkpoint files, and any child
process the payload spawns, including `harvest.py`.

`umask` does not alter an existing directory, so a loot directory inherited from
an earlier release is explicitly `chmod 0700`. That call fails closed. `exit`
rather than `return` is deliberate: the library is sourced, so `return` would
merely end the `source` and let the payload continue writing into an unprotected
directory — the exact fail-open the change exists to prevent.

### Atomic report writes

`harvest.py` creates an `O_EXCL` 0600 temporary file and `os.replace()`s it over
the destination. Opening the destination directly is insufficient because
`O_CREAT`'s mode argument applies only when the file is created: a report left
by an earlier run would be opened at its existing mode and hold the evidence
there for the whole write, with a `chmod` afterwards closing the door too late.
`O_EXCL` prevents adopting a stale temporary file, and the rename is atomic.

Atomicity alone only survives a killed process. Without a barrier the rename can
reach the disk before the data does, leaving a report that exists but is empty —
so the temporary file is `fsync`ed before the rename and the parent directory is
`fsync`ed after it. A reader therefore sees either the previous report or the
complete new one, never a partial file. The Pager runs on battery and a scan is
exactly when it may lose power, which is why this costs two syncs on a file of a
few kilobytes.

### Reproducible packaging across hosts

`scripts/package-release.sh` generated `SHA256SUMS` with a bare `sort`, which
honours `LC_COLLATE`. A C-locale host — every CI runner — orders
`./docs/V3-RESEARCH.md` before `./docs/architecture.dot`; an `en_US.UTF-8` host
reverses them. Same content, different bytes, different archive digest, while
every per-file hash still verified. That defeated independent verification:
rebuilding from source to confirm a published checksum produced a mismatch.
Manifest generation now pins `LC_ALL=C`, and `scripts/check.sh` asserts the
manifest is in C-locale byte order.

haptic paths were exercised and share the same invocation contract as audio.

## Rollback

If on-device validation reveals a release-blocking problem:

1. Stop using the v3.4.0 payload entries.
2. Reinstall the v3.3.0 release payloads from its immutable tag/assets.
3. Preserve `/root/loot/clawhunter/` before changing payload files.
4. Note that loot directory permissions tightened by v3.4.0 are not reverted by
   downgrading; run `chmod 0755` if a v3.3.0 workflow depended on the old mode.
5. Record firmware version, mode, log evidence, and exact reproduction before
   reopening rollout.

Do not move or overwrite the published `v3.4.0` tag. A correction must use a new
semantic version.

## Research

No new *external* research was required: no Hak5 or OpenClaw documentation was
consulted and no protocol behaviour changed. The payload-launch fix is
firmware-dependent, but the contract behind it was established empirically on
the device — see the launch details above — and is recorded in `AGENTS.md`.
`docs/V3.3-RESEARCH.md` remains the current research record and is unchanged;
the research record tracks findings, not version numbers.
