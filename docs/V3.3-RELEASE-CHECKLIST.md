The release notes expose this limitation and list the physical checks required for follow-up. Rollback criteria are documented. No automated or source-level gate is failing.

### Chronology Note

The implementation commit was fast-forwarded to `main` after its release-branch
workflow passed, and the resulting `main` workflow also passed. That happened
before the request to create a pull request, while GitHub CLI authentication was
unavailable in the release environment. Consequently, GitHub cannot create a
normal implementation PR between `release/v3.3.0` and `main`: both refs already
identify the same implementation commit.

This follow-up PR therefore adds only this evidence record. It is deliberately
not presented as containing the already-landed implementation. Its purpose is to
provide a reviewable final release gate, preserve the GitHub chronology, and
require one last `Quality` result before the immutable tag is created.

## Remaining GitHub Sequence

1. Commit and push this evidence record on `release/v3.3.0`.
2. Open a pull request that discloses the chronology above and contains only the evidence diff.
3. Require the pull request's `Quality` workflow to pass, then merge it without rewriting default-branch history.
4. Create one annotated `v3.3.0` tag on the reviewed merge commit.
5. Push the tag; the `Release` workflow rebuilds, re-runs the gate, and publishes checksummed assets.
6. Verify the GitHub release URL, asset checksums, workflow result, and tag target.

An existing tag or release is a hard stop. Published tags/assets are immutable; corrections require a new version.
