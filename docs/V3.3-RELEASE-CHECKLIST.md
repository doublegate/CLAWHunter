### Defect found during physical validation

Loot was created world-readable (0644), and the loot directory 0755. Scan output
names third-party hosts and records harvested evidence about them, so it is
operator-sensitive even on a single-root device.

Fixed in three parts:

- `lib/common.sh` sets `umask 077` before the first write, which also covers
  checkpoints and any child process the payload spawns.
- `umask` does not alter an existing directory, so a loot directory inherited
  from an earlier release is explicitly `chmod 0700`. That call **fails closed**:
  a swallowed failure would leave the directory world-readable with no signal.
  `exit` rather than `return` is deliberate — the library is sourced, so `return`
  would merely end the `source` and let the payload continue unprotected.
- `harvest.py` writes a fresh `O_EXCL` `0600` temp file and `os.replace()`s it
  over the destination, so a documented standalone invocation does not depend on
  the caller's umask.

The first attempt at the third part opened the destination directly with
`os.open(..., 0o600)`. Review caught that this is insufficient: `O_CREAT`'s mode
applies **only when the file is created**, so a report left by a pre-fix run was
opened at its existing `0644` and held the evidence at that mode for the whole
write, with the `chmod` closing the door too late. The temp-and-replace form has
no such window, and additionally makes the write atomic — a crash mid-scan now
leaves the previous report intact rather than truncated.

Verified after the fix: report `-rw-------`, loot directory `drwx------`, loot
file `-rw-------`; a report seeded at `0644` ends the run at `0600` with no
leftover temp file; and with `chmod` forced to fail the library refuses to run.

Confirmed safe on this firmware: both `pineapple` (the port-1471 web UI) and
`pineapd` run as root, so restricting loot does not break the Portal results
view.

## Reproducibility Defect Found During Verification

Verifying the published archive against a local rebuild surfaced a real defect,
now fixed in this same change set.

The CI artifact hashed `0d408817…` while a local rebuild produced `344f8943…`.
Every per-file hash verified, the file set and all tar metadata matched, and
`SHA256SUMS` passed — the sole difference was the *ordering of lines inside*
`SHA256SUMS`. `package-release.sh` generated the manifest with a bare `sort -z`,
which honours `LC_COLLATE`: a C-locale host (every CI runner) orders
`./docs/V3-RESEARCH.md` before `./docs/architecture.dot`, while an `en_US.UTF-8`
host reverses them.

This defeated independent verification. A downloader rebuilding from source to
confirm the published checksum would get a mismatch and reasonably conclude the
release was tampered with, while every internal check reported success.

`scripts/check.sh` could not have caught it: it builds twice on one host under
one locale, so both builds share the same collation. Two changes close this:

- `package-release.sh` now pins `LC_ALL=C sort -z` for manifest generation.
- `check.sh` now asserts the manifest is in C-locale byte order.

Confirmed after the fix: building under both `LC_ALL=C` and `LC_ALL=en_US.UTF-8`
reproduces the published `0d408817…` byte-for-byte. The published v3.3.0 assets
are unaffected and require no reissue — CI built them in the C locale, which is
the order the fix standardises on.

Note one limit of the new assertion: on a C-locale host it passes trivially,
since the manifest is already in C order there. It therefore protects
contributors on dictionary-collation desktops — where the divergence originates —
rather than CI.
