## Reproducibility Defect Found During Verification

Verifying the published archive against a local rebuild surfaced a real defect,
now fixed in this same change set.

The CI artifact hashed `0d408817…` while a local rebuild produced `344f8943…`.
Every per-file hash verified, the file set and all tar metadata matched, and
`SHA256SUMS` passed — the sole difference was the *ordering of lines inside*
`SHA256SUMS`. `package-release.sh` generated the manifest with a bare `sort -z`,
which honours `LC_COLLATE`: a C-locale host (every CI runner) orders
`./docs/V3-RESEARCH.md` before `./docs/architecture.dot`, while an `en_US.UTF-8`
host reverses them.

This defeated independent verification. A downloader rebuilding from source to
confirm the published checksum would get a mismatch and reasonably conclude the
release was tampered with, while every internal check reported success.

`scripts/check.sh` could not have caught it: it builds twice on one host under
one locale, so both builds share the same collation. Two changes close this:

- `package-release.sh` now pins `LC_ALL=C sort -z` for manifest generation.
- `check.sh` now asserts the manifest is in C-locale byte order.

Confirmed after the fix: building under both `LC_ALL=C` and `LC_ALL=en_US.UTF-8`
reproduces the published `0d408817…` byte-for-byte. The published v3.3.0 assets
are unaffected and require no reissue — CI built them in the C locale, which is
the order the fix standardises on.

Note one limit of the new assertion: on a C-locale host it passes trivially,
since the manifest is already in C order there. It therefore protects
contributors on dictionary-collation desktops — where the divergence originates —
rather than CI.
