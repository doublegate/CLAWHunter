# CLAWHunter v3.3 Research Record

Research date: 2026-08-06

This record captures the current external facts used to update CLAWHunter from v3.2.0 to v3.3.0. Official documentation and source were treated as authoritative. Community reports were used only to identify operational failure modes worth guarding against. The final publication audit re-read Hak5's complete `llms-full.txt` manual export and sitemap, not only the landing and payload-summary pages.

## Official Pager payload source review

The official Hak5 payload repository defines three top-level libraries: `library/user`, `library/recon`, and `library/alerts`. The publication audit was pinned to current `master` commit `377e87334a03166658600aa9fa5aefe896b1a85f` (2026-08-05), after reviewing its recent commit history for category/index/header changes. Relevant current category locations are:

- user: `library/user/reconnaissance`
- recon: `library/recon/access_point`
- alert: `library/alerts/pineapple_client_connected`

The official Connect-To-AP payload shows that hidden APs require an explicit SSID prompt and that `WIFI_CONNECT` receives interface, SSID, encryption, password, and selected BSSID. Its current mappings are `open`, `psk`, `psk2`, and `sae`. The Pager client interface used here is 2.4 GHz, so CLAWHunter rejects selected access points outside that capability rather than reporting a misleading connection failure.

The client-connected alert provides `_ALERT_CLIENT_CONNECTED_CLIENT_MAC_ADDRESS` and `_ALERT_CLIENT_CONNECTED_SSID`. `FIND_CLIENT_IP` is the preferred resolver. A fallback must match the triggering MAC exactly; selecting the final ARP row can target the wrong host.

The repository also requires self-contained payload resources and warns against live staged code. v3.3.0 release archives therefore embed a byte-identical `common.sh` beside every payload.

### Payload contract details applied

| Contract | Current use in v3.3.0 |
| --- | --- |
| Metadata header | Title, description, author, version, and alert category remain at the top of entry points |
| User category | `user/reconnaissance/clawhunter` |
| Recon category | `recon/access_point/clawhunter` |
| Alert category | `alerts/pineapple_client_connected/clawhunter-watchdog` |
| Recon SSID | `_RECON_SELECTED_AP_SSID` |
| Recon hidden flag | `_RECON_SELECTED_AP_HIDDEN`; prompt for exact SSID when true/empty |
| Recon encryption | `_RECON_SELECTED_AP_ENCRYPTION_TYPE` |
| Recon BSSID | `_RECON_SELECTED_AP_BSSID` |
| Recon band guard | numeric frequency when present, otherwise numeric channel |
| Connect call | `WIFI_CONNECT wlan0cli SSID ENC PASSWORD BSSID` |
| Alert MAC | `_ALERT_CLIENT_CONNECTED_CLIENT_MAC_ADDRESS` |
| Alert SSID | `_ALERT_CLIENT_CONNECTED_SSID` |
| Alert IP lookup | `FIND_CLIENT_IP MAC 1`, then exact-MAC `/proc/net/arp` fallback |
| Payload resources | local `common.sh` and user-mode `harvest.py` included in the release archive |
| Haptic command | `VIBRATE` receives a ringtone filename or complete RTTTL pattern |

The path resolver supports three cases in priority order: local Portal resource, installed `/root/payloads/lib/common.sh`, and repository-root `lib/common.sh`. This makes the deployment contract explicit and testable without depending on one firmware variable's formatting.

## OpenClaw gateway review

Current OpenClaw documentation and source establish:

- Default gateway HTTP/WebSocket port: `18789`.
- Gateway Bonjour service: `_openclaw-gw._tcp`.
- mDNS TXT properties are unauthenticated hints and must not be authoritative.
- Liveness and readiness endpoints: `/healthz` and `/readyz`.
- A successful WebSocket transport sends `connect.challenge`; authenticated clients sign the challenge-bound device payload with a persistent Ed25519 device identity.
- Current clients should not send the old unauthenticated agent-turn frames.
- `POST /tools/invoke` accepts `tool`/`name`, optional `action`, and tool-specific `args`.
- Shared token/password authentication is full trusted-operator authority, not a narrow read scope.
- The HTTP tool endpoint has a default deny list for command execution, file mutation, session spawning, scheduling, gateway control, and node relay.

### Protocol surface details applied

| Surface | v3.3.0 behavior | Trust decision |
| --- | --- | --- |
| TCP 18789 | Default active target | Reachability only |
| TCP 18790 | Optional legacy secondary target | Reachability only |
| `_openclaw-gw._tcp` | Parse resolved IPv4 and SRV port | Hint only; TXT is unauthenticated |
| HTTP/S `/` | Record status, headers, capped body | Generic response is a candidate signal |
| `/healthz` | Record liveness status/body | Generic 200 is weak; marker body is specific |
| `/readyz` | Record readiness status/body | Generic 200 is weak |
| WebSocket `/` | Validate HTTP 101 and accept hash | Upgrade alone is weak |
| `connect.challenge` | Record first protocol event | Strong product-specific evidence |
| device connect/pairing | Not attempted | Requires persistent Ed25519 identity and explicit approval |
| `/tools/invoke` | Literal `sessions_list`, then `memory_search` allowlist | Only with operator-supplied authorized secret |
| `/v1/responses` | Not used | Optional surface adds no needed evidence |
| legacy canvas path | Compatibility probe in non-fast mode | Low-weight hint only |

OpenClaw's security documentation is material to credential handling: a shared gateway token/password is full operator authority even if CLAWHunter itself calls only read-oriented tools. v3.3.0 therefore avoids command-line secrets, does not print the token, stops on authentication/policy responses, and never broadens the tool list based on target data.

Decisions:

- Treat `connect.challenge`, an `x-openclaw` header, or an OpenClaw body marker as specific confirmation evidence.
- Do not confirm generic 401/403 responses, generic health endpoints, or a generic WebSocket upgrade.
- Keep 18790 only as a legacy secondary probe.
- Do not implement Ed25519 pairing on constrained Pager shell code; record the challenge and stop.
- Replace the obsolete multi-turn command protocol with bounded HTTP evidence and two explicitly read-only tool calls (`sessions_list` and `memory_search`) when the operator supplies an authorized secret.
- Never place that secret in argv or logs.

## Community cross-check

GitHub topic and repository searches were reviewed for Pager payload layouts, hardware-access approaches, dependency practices, and alert behavior. Reddit Pager discussions were reviewed for current operational reports. A June 2026 report described alert discovery/triggering problems on firmware 1.0.9 despite correct directory and permissions. This is not proof of a CLAWHunter defect, but it reinforces the 1.1.0 recommendation because Hak5 lists monitor-interface stability work in that release.

No community payload code was copied. Community sources were advisory only.

Repositories/topics reviewed included:

- Hak5's official Pager Payload Library for authoritative categories, metadata, event variables, UI calls, and connection examples.
- The `wifi-pineapple` and `wifi-pineapple-pager` GitHub topic indexes for actively maintained Pager payload suites and device libraries.
- `sinXne0/pineapple-pager-payloads` and related official-repository forks for directory/packaging comparisons.
- `bad-antics/nullsec-pineapple-suite` for breadth of current community category/dependency patterns; no code was adopted.
- `pineapple-pager-projects/pineapple_pager_pagerctl` for awareness of native hardware-control alternatives; CLAWHunter remains on supported shell/DuckyScript interfaces.
- Reddit Pager reports concerning alert payload discovery/triggering, firmware stability, and payload installation paths.

Community conclusions were limited to operational safeguards: use standard category paths, executable payloads, self-contained resources, current firmware, explicit timeouts, and non-fatal hardware feedback. Community descriptions were not treated as protocol authority.

## Implementation outcomes

The research produced these v3.3.0 changes:

1. Moved all payloads to official library-compatible category paths.
2. Corrected recon hidden-SSID, encryption, BSSID, selected-band, and connection handling.
3. Corrected alert variables and exact-client IP resolution.
4. Updated detection to the current default port, exact mDNS service, health endpoints, and challenge protocol.
5. Added evidence scoring that separates confirmed targets from weak candidates.
6. Replaced obsolete harvest behavior with a bounded current-protocol assessment.
7. Added eMMC environment bootstrapping and protected credential loading.
8. Fixed sequential/parallel checkpoint parity and port-set identity.
9. Kept IPv6 link-local discovery separate from IPv4 scan and sort paths.
10. Added automated quality checks, deterministic release packaging, checksums, and an installer.
11. Replaced numeric haptic calls with the Pager's documented RTTTL `VIBRATE` contract.

Physical Pager validation remains a release-environment activity; host tests cannot validate RF behavior, theme rendering, or hardware feedback timing.
